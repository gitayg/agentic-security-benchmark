# Methodology

Instructions for measuring an agentic-security product against the corpora and harness in this
repository. Written for someone grading **their own** product.

Read [`./AMTSO.md`](./AMTSO.md) first — it defines the outcome vocabulary this document assumes.

---

## 1. What this measures, and what it cannot

**It measures** whether a product detects or prevents constructed attack samples put to it through a
defined entry point, and how often it fires on benign work put to it the same way, reported as a
distribution of outcomes across a labelled taxonomy.

**It cannot measure** field effectiveness. Every sample here is **authored**, not captured from a live
incident. What a result describes is how a product behaves against **attacks somebody knew how to
write** — which is a narrower claim than "how safe is my agent", and is worth exactly as much as the
corpus is representative. Section 9 lists the specific limits.

It also cannot make a self-run number an independent one. Nobody here is a testing lab. What the
method offers instead is that the corpora, the harness and the split algorithm are all public, so a
disagreement about a result is checkable rather than a matter of trust.

---

## 2. The locked split

A held-out set is a **consumable**. It measures generalisation exactly once per decision made in
ignorance of it, and every look costs some of that.

### Split once, stratified by family AND transformation axis

Divide a corpus a single time into a **tune half** and a **locked test half**, stratified so both
halves carry the same mix of attack families **and** the same mix of transformation axes.

Stratification is not decoration. An unstratified random split can hand one half **every homoglyph
sample**, and the score then measures *which bucket landed where* rather than whether the detectors
generalise.

### Deterministic, with no stored seed

Within each stratification bucket, **sort samples by id** and assign them to the two halves
**alternately** — even index to `tune`, odd index to `test`. There is no random number generator and
therefore **no seed to record, lose or quietly change**: the split is **recomputable from the corpus
alone**.

The exact algorithm, for the corpora in this repository:

> Bucket every sample by its stratum — for the attack corpus, `(family, axis)`; for the web-content
> corpus, `(channel, hard_negative)`. Sort by `id` inside each bucket. Assign alternately: even index
> → `tune`, odd index → `test`. Then never open the `test` half while tuning.

Anyone with the corpus derives the same two halves you did.

### The test half is a file boundary, not an intention

"We tried not to look at it" is not a control. Detector work opens the tune half; **the locked half is
a separate file that the tuning wave does not open at all.**

The reason is that **tuning against a held-out set silently converts it into a training set** — not
through cheating, but through ordinary iteration. Each time a threshold is nudged, a pattern widened,
or a wave of rules shipped *because the held-out score moved*, information from that set has entered
the detectors, and the number it produces afterwards describes **memorisation rather than
generalisation**.

**Nothing about the set looks different once this has happened.** There is no marker, no diff, no
warning. That is exactly why it has to be prevented **structurally** rather than noticed later.

### A burned set is retired, not reused

This rule exists because it was broken. An earlier held-out set in the reference implementation **was
tuned against, and thereby destroyed as a generalisation measure**. The information cannot be taken
back out of the detectors, so there is no way to un-burn it.

It was **retired rather than quietly re-used with a caveat**, and a fresh set was generated by a
mutation pass that deliberately does not read the detectors. Reusing it would have produced a **higher
number and a worse measurement**.

If you burn yours, retire it. A caveat on a burned set is a caveat on a number that no longer means
anything.

### The gap between the halves is itself the finding

Score **both** halves and report **both**. The difference between the tune half's score and the locked
half's score is published as the **overfit margin**.

A method that reports only the locked score discards the one measurement that says how much of the
tuning was fitting rather than detecting.

### What this repository publishes, and what it withholds

**This repository publishes the tune halves and withholds the locked test halves on purpose.**

[`corpora/benign-web-content-tune.json`](./corpora/benign-web-content-tune.json) is **158 published
samples** — exactly half of a **311-sample** corpus. The other **153 samples**, the `test` half, are
withheld, and so is a separate held-out attack set. The file records the withheld count and the
algorithm in its own `_heldOutSplitWithheld` block, so the omission is visible in the data rather than
only in prose.

Both withheld sets are nonetheless **public** in the MoorAI repository, so every number in
[`./results/`](./results/README.md) can be reproduced by a third party. Publishing a held-out set does
not destroy it; TUNING against it does, and that is the rule we hold ourselves to. Being public means
you can check us rather than take our word for it. No contribution to a locked split is accepted from
outside, because a split's provenance depends on it being fixed before anyone saw a score.

**Any vendor doing this properly should keep their own.** The algorithm above needs no stored seed, so
you can generate a locked split from any corpus you have, including the published tune halves. Then
never open it while tuning.

## 3. Baseline validation

**A sample counts only if the malicious outcome could actually occur with the product absent.** An
attack that resolves to nothing executable, or that targets a capability the agent does not have, is
an **invalid sample — not a miss, and equally not a catch**. On the enforcement side, confirm the
action **actually executes** with the product out of the path before scoring it as prevented.

Full statement of the rule and why it deliberately costs you both ways: **[`./AMTSO.md`](./AMTSO.md)
§5**. Per-sample rationales: **[`./corpora/README.md`](./corpora/README.md)**.

The second baseline — subtracting what the underlying model refuses unaided — is **[`./AMTSO.md`](./AMTSO.md)
§3**, and it is the one most likely to change your number.

## 4. Right-reason scoring

A catch is additionally scored **right-reason** or not: credited to a rule that matches the sample's
**actual attack class**, rather than a coincidental match by an unrelated rule.

An incidental catch is a **real detection** — do not throw it away. But it is worse than a right-reason
catch in two specific ways:

1. **The categorization a security team sees is wrong.** The alert names the wrong thing, so triage,
   routing and policy all act on a mislabel.
2. **It is a much weaker guarantee of generalisation.** It does not survive the attacker changing the
   one thing the unrelated rule happened to match — a keyword, a formatting quirk, a URL shape. A
   right-reason catch survives that; an incidental one is one edit away from a miss.

**Report the right-reason rate SEPARATELY from recall wherever it is materially below it.** A recall
figure that is largely incidental is a different result from one that is largely right-reason, and the
headline cannot tell them apart.

### The limitation in this repository, stated plainly

Right-reason scoring here uses the corpus field **`expectThreat`**, which holds **MoorAI's own threat
ids**. It is therefore **only meaningful for a product that shares that id space.** For every other
adapter, the right-reason column is not a comparable number and should not be quoted as one.

**A vendor-neutral right-reason label is an open problem.** A shared attack-class vocabulary that
products could map their own categories onto would fix it. Proposals are welcome — see
[`./CONTRIBUTING.md`](./CONTRIBUTING.md).

## 5. Detection is not prevention

Feed every sample through **the entry point a real prompt or tool call takes**. Do not call a detector
function in isolation.

The distinction is not pedantic, and here is the concrete case that proves it:

> A library-level harness scored **full marks** on a cross-agent capability — and **nothing on the
> enforcement path was calling it.** The finding existed; no deployment could ever see it. An
> end-to-end reachability harness had to be written to expose that, one that refuses to call the
> library at all and instead drives the two paths a real deployment actually has, counting only what
> arrives at the far end.

**A detector with no caller measures nothing, however well it scores in a script.**

The generalisable practice: keep a **stage-reachability table** — for each stage the engine defines
(`prompt`, `file`, `output`, `index`, `tool`), record **which shipping code path actually feeds it**,
established by reading the call sites rather than assumed. Anything unreachable is a **reachability
finding, not a detection result**: a corpus scored only through the library API.

Keep the table even after every cell is reachable, and **re-ask the question after every wave**:
*which stages does a shipping harness actually feed?* New detectors arrive faster than new callers.

Related: which stage a sample can be reached at is a **property of the sample, not a choice**.
Supply-chain samples are tool metadata and config files reachable only at the tool, file and index
stages; cross-agent samples may be sequences, or event-graph shapes with no text at all. For
sequences, report the **optimistic** reading (`anyStep` — anything fired at any step) and the
**strict** reading (`consumeStep` — something fired at the step where the payload was actually
consumed) **separately, and never interchangeably.** The strict one is the number that matters: a
payload written before the product was installed is only ever seen at consume time, so a detection
that exists only at write time does not stop the attack.

## 6. Falsification discipline

Five rules. Each one costs a number.

### 1. A test that has never been observed failing is not evidence

Break the production line. Confirm the test goes **red**. Revert. **Record what was broken.** Until
that is done, a green assertion is a green light with no wiring behind it.

**The worked example, which is the whole argument:**

> A benign fixture produced **zero findings at every stage**. It carried an assertion that its clean
> result must not silently mean "never scanned" — and that assertion was **green**.
>
> It would also have been green **on the day the scan was deleted**, because from outside the harness
> **zero findings and no scan are the same observation.**
>
> Only breaking the production line — removing the scan and confirming the test goes red —
> distinguishes them. Until then, the assertion is decoration.

Every claim you publish should have a test that has been **seen red**.

### 2. Locked splits the tuning work never opens

Section 2. The rule that most reliably lowers a headline number, and the only one that makes the
number mean generalisation.

### 3. Both baselines run underneath every coverage figure

Validity (§3) and model refusal ([`./AMTSO.md`](./AMTSO.md) §3). Both **remove** credit rather than
adding it. Neither is optional if the number is going to be compared to somebody else's.

### 4. Repeated runs, with variance reported

Anything involving a model is a **sample from a distribution**. A single passing run is a point
estimate presented as a fact. Run model-involved measurements **N times** and publish the **spread**
and per-sample stability, not a lucky single pass.

This is not hypothetical: model-assisted figures have been watched moving between runs — a judge
recovering a different number of attacks on consecutive runs, a benign false-positive count drifting.
If you report a single model-assisted number you are reporting one draw.

### 5. The deterministic number is always the headline

The **deterministic, LLM-free** figure is the headline. A **model-assisted** figure is reported
**separately** and **never merged into it**. Put the model-assisted path behind an explicit flag that
the default run does not import, so a headline number can never quietly become model-assisted.

## 7. Reproducibility

Four properties, each of which someone else has to be able to check.

1. **The headline path is deterministic and model-free.** Every sample carries a ground-truth
   `shouldDetect` label; the default scoring run compares the product's verdict to that label with **no
   model anywhere in the loop**. Coverage, precision and recall from that path are identical on any
   machine.

2. **Splits are derivable, not seeded.** Recompute the tune/test split by sorting and alternating
   rather than sampling — no seed to publish, and none to get wrong. See §2.

3. **Any model is pinned by digest, not by tag.** A tag moves; a digest does not. Where the reference
   implementation involves a model at all — the refusal baseline and the optional semantic-escalation
   judge — it is one local build of `llama3:latest` (8B). A digest is what makes "the same model"
   checkable a year from now. **But recording a digest is not pinning one**: the reference
   implementation's two published descriptions of that model disagree on its quantization, and the
   digest appears only in prose and nowhere in the code, so nothing in a run asserts it. Have your
   harness read the digest back from the runtime and fail on a mismatch. See
   [`./AMTSO.md`](./AMTSO.md) §3.

4. **Everything runs on-device.** **No API key, no scoring service, no network call** anywhere in the
   measurement path. Corpora are never sent to a third party and results are never adjudicated by a
   remote judge. This is not only a privacy property — **it is what makes repeated runs, and therefore
   honest variance reporting, affordable at all.** A baseline that costs money per sample gets run
   once, and a baseline run once is not a baseline.

## 8. How to grade your own product

1. **Write an adapter.** The interface is small; its required surface is a **single scan method**. The
   contract is documented in [`./scorers/README.md`](./scorers/README.md) — read it there rather than
   inferring it from this page. Declare honestly which harnesses you implement: a harness you do not
   declare produces `not-applicable` rows, which are excluded from every rate, and that is strictly
   better for everyone than appearing to have missed samples you were never shown.

2. **Run the harness** over the corpora in [`./corpora/`](./corpora/README.md). Partial runs are fine
   and are more honest than a padded total — say which corpora you ran.

3. **Keep your own locked split.** Use the algorithm in §2 on a corpus of your own, or on the
   published tune halves. Never open the test half while tuning. Publish the overfit margin.

4. **Run your model-refusal baseline** against the model your agent actually runs, over repeated runs
   per family, and state which model it was. A detection rate that has not subtracted what the
   underlying model refuses unaided is **not comparable** to one that has.
   ([`./AMTSO.md`](./AMTSO.md) §3.)

5. **Publish the distribution**, not a headline — every bucket including the zeros, recall and
   false-positive rate on separate lines, `prevented` and `preventedHard` both.
   ([`./AMTSO.md`](./AMTSO.md) §6.)

6. **Submit a results file.** What it must state, and how to open the PR, is in
   [`./results/README.md`](./results/README.md).

## 9. Limits

Stated plainly, because a limit you have to discover for yourself is a limit that was hidden.

### Constructed corpora, not captured incidents

Every attack sample is **written**. None is a captured live incident, and no telemetry from a real
deployment feeds these corpora. What a result describes is behaviour against **attacks somebody knew
how to write**. Mutation and closed-loop generation widen that set beyond one author's imagination,
and the refusal baseline stops the easy half being credited — but **neither converts a constructed
corpus into field evidence.**

### Enforcement measurement is scoped to a single agent host

In the reference implementation, prevention is measured against **one agent host**, because that is
where a `PreToolUse` hook exists to enforce at. Other hosts are covered at the detection layer, and a
**detection claim is not an enforcement claim**. Any statement that a malicious tool call was
*blocked* should be read as **scoped to the host it was measured on**.

### An 8B local proxy, not a frontier model

The refusal baseline and the optional semantic judge run on `llama3:latest` (8B). A frontier
model refuses more **and decodes obfuscated payloads far better**. Inspection showed the 8B model
frequently **not complying** with obfuscated attacks so much as **failing to decode** them. A
meaningful share of measured marginal value on the obfuscation families is therefore **soft**. See
[`./AMTSO.md`](./AMTSO.md) §3.

### The corpora are still weighted toward vector 1, and vector 6 has no dedicated set

**Vector 1 (direct input) is over-represented** across the wider labelled set, because it is the
easiest vector to author. The four dedicated per-vector corpora — vector 2 (45 attacks / 17 benign),
vector 3 (72 / 25), vector 4 (57 / 24) and vector 5 (42 / 25) — exist to counteract that, and each
enumerates its own sub-techniques so the spread inside a vector is inspectable rather than asserted.
The imbalance has **not** been eliminated. **Vector 6 (static code artifact) has no dedicated corpus
here at all.**

### One "benign" corpus is not entirely benign

[`corpora/benign-web-content-tune.json`](./corpora/benign-web-content-tune.json) is **149 benign + 9
attack** samples, not 158 benign. The nine are prompt-injection tutorial pages, deliberately
reclassified from hard negatives to `shouldDetect: true` on the reasoning that an injection example
on a tutorial page is a **live payload** — the agent fetching it cannot distinguish teaching material
from an attack, because the text is identical either way.

Worth studying before you relabel anything of your own: that change **cut both ways**. It lowered the
false-positive rate, because those had never been false positives — and the same relabel turned two
pages that do *not* fire from "correct allows" into **misses that had previously been invisible**.
A relabel that only ever improves your number is a relabel to be suspicious of.

The file's header comment and those nine samples' `validity` strings are now **stale** and still
argue the old label. They are republished unedited here; see
[`./corpora/README.md`](./corpora/README.md).

### Right-reason scoring is not vendor-neutral

It is keyed to one product's threat-id space. See §4.

### No independent tester has reproduced any of it

Every figure in [`./results/`](./results/README.md) is **self-run**, by whoever submitted it, on
corpora that are authored rather than captured. No third-party lab has verified, reproduced or audited
any of it. The mitigation on offer is not a certificate but a repository: the corpora, the harness and
the split algorithm are public, so **the falsifiable version of this page is somebody re-running it
and disagreeing.**

### AMTSO has not reviewed, certified or endorsed this benchmark

**AMTSO has not reviewed, certified or endorsed this benchmark, its corpora, its harness, or any
result published here.** The *Guidelines for Testing of Agentic Security Products v1.0* are cited as
published criteria this repository grades against. That is **self-assessment, not accreditation**.
